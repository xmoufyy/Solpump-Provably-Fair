# Solpump Fairness Lab

An independent, local verification and auditing tool for Solpump's provably-fair **Crash**, **Blackjack**, **Keno** and **Mines**.
It rebuilds game outcomes from revealed seeds, compares them with recorded outcomes, keeps an audit history in SQLite, and exports reproducible reports.

It is read-only: no betting, no wallet, no keys, and no automation of play.

> **Version 2.0** is the result of a full code audit. See [`docs/COMPREHENSIVE_AUDIT.md`](docs/COMPREHENSIVE_AUDIT.md) for findings and fixes, [`docs/CRYPTOGRAPHIC_PARITY_REPORT.md`](docs/CRYPTOGRAPHIC_PARITY_REPORT.md) for how the algorithms were validated (and what remains unconfirmed), [`docs/PERFORMANCE_REPORT.md`](docs/PERFORMANCE_REPORT.md), and [`docs/CHANGELOG_V2.md`](docs/CHANGELOG_V2.md). The follow-up audit of 2026-10-24 is in [`docs/AUDIT_2026-10-24.md`](docs/AUDIT_2026-10-24.md).

## Quick start (Windows)

1. Install **Node.js 22.13 or newer** (it has the built-in `node:sqlite` module).
2. Double-click **`start.bat`**. On first run it installs dependencies, builds the UI, starts the server and opens `http://localhost:8787`.

| Script | Purpose |
|---|---|
| `start.bat` | Production mode (single server on port 8787; set `PORT` to change it) |
| `start-dev.bat` | Development mode: API with reload on :8787, Vite UI on :5173 |
| `test.bat` | Every quality gate (`npm run audit:all`): types, lint, unit + parity, independent Python parity, integration, build, browser tests, `npm audit` |

Audit history is stored in `data/fairness-lab.db` and survives restarts. When a newer version needs a schema change, the app migrates the database at startup. If the database already holds data, it first writes a backup to `data/backups/`.

Settings → **Create database backup** writes a consistent snapshot at any time. To restore one, stop the app and replace `data/fairness-lab.db` with the backup file.

To try batch verification, import `fixtures/sample-import-synthetic.csv`. It holds 27 **synthetic** rounds generated by the independent reference implementation, with 2 deliberately wrong rows.

## Where the algorithms come from

**Read this first.** At build time (2026-10-19), the official pages (`solpump.io/fairness/{crash,blackjack,keno,mines}`) were behind a bot-verification challenge and could not be fetched automatically. The challenge was not bypassed.

The implementations here are **transcriptions of the reference code supplied in the project specification**, which states that it reproduces the published code. Before relying on this tool for real compatibility claims:

* compare `backend/src/games/*.ts` and `tests/reference-parity/reference/official.mjs` against the live fairness pages, and
* verify a few of your own real, historical rounds whose outcomes you saw in the Solpump UI.

If Solpump has changed an algorithm, add it as a **new version**. Don't edit the existing one.

## The algorithms

Notation: `HMAC(key, m1, m2, …)` means HMAC-SHA256 with `key`, updated with each message part in order and **no separators**. Every string is UTF-8 encoded exactly as entered. Nothing is trimmed or normalised.

### Crash (`crash_hmac_sha256_v1`)

```
digest = HMAC(serverSeed, publicSeed)                  // hex
if BigInt("0x" + digest) % 20 == 0  → 1.00x             // full 256-bit digest
h = parseInt(digest[0..13], 16)                         // first 52 bits
e = 2^52
multiplier = floor((100·e − h) / (e − h)) / 100         // IEEE-754 double maths, as in JS
```

There is no nonce.

### Blackjack (`blackjack_hmac_sha256_card_v1`)

```
for cardNumber = 1, 2, 3, …
  hash = HMAC(serverSeed, clientSeed, String(cardNumber))   // "seed" + "1", no separator
  h = parseInt(hash[0..13], 16)
  rank = ["2".."10","J","Q","K","A"][h % 13]
  suit = ["hearts","diamonds","clubs","spades"][h % 4]
```

Each card is independent, so there is no deck, no Fisher-Yates shuffle, and duplicates are possible. The lab checks the numbered card sequence. It does **not** assign cards to the player or dealer, because that order is not part of the published algorithm.

### Keno

Board: Classic, Low, Medium and High use **40** numbers. Extreme uses **56**. Every mode draws **10**.
The player's 1–10 picks and the risk level are **not** inputs to the draw. Risk only changes payouts (and the board size for Extreme).

* **`hmac_sha256_v2`**
  * `transcript = enc("solpump:provably-fair:hmac-sha256:v2") ‖ enc("keno") ‖ enc(clientSeed) ‖ enc(nonce)`, where `enc(x) = uint32be(byteLength(x)) ‖ utf8(x)`.
  * Block *n* is `HMAC(serverSeed, transcript, uint32be(n))` for n = 0, 1, …, read as eight big-endian uint32 values.
  * `nextIndex(max)` uses rejection sampling: reject `v ≥ 2³² − (2³² mod max)`, then return `v mod max`.
* **`seedrandom_v1`** (legacy): `rng = seedrandom(serverSeed + ":" + clientSeed + ":" + nonce)` and `index = floor(rng() · max)`.

Draw: from the list `[1..tileCount]`, repeat 10 times: take `index = nextIndex(list.length)`, record `list[index]`, then remove it. The draw order is preserved.

### Mines

Grids are 3×3, 5×5, 6×6, 7×7 and 8×8 (9, 25, 36, 49 and 64 tiles), with 1 to tiles−1 mines. "Difficulty" is just the grid size plus the mine count.

* `privateSeed = serverSeed + ":" + clientSeed + ":" + nonce`
* **`hmac_sha256_v2`** uses the same generator as Keno, but:
  * the **HMAC key is `privateSeed`**, not the server seed, and
  * the transcript is `enc(label) ‖ enc("mines") ‖ enc("") ‖ enc("0")`, with a literal empty string and `"0"`.
* **`seedrandom_v1`**: `seedrandom(privateSeed)`.

Placement: from the positions `[0..tiles−1]`, repeat once per mine: remove `positions[nextIndex(positions.length)]`. Indices are **zero-based, row-major**. The board shows both 1-based labels and the 0-based `#n` index.

The algorithm version for Keno and Mines must always be **stated**. The lab never picks a version because it happens to match.

## What each kind of evidence proves

| Evidence you have | What the lab can show | What it cannot show |
|---|---|---|
| Revealed seeds (+ nonce/settings) only | **Reconstructed**: the outcome the published algorithm produces from those inputs | Whether that was the real outcome |
| Seeds + recorded outcome | **Match / Mismatch**: whether the recorded outcome agrees with the seeds | That the seeds were fixed before the round |
| … + commitment hash you supply | The candidate `SHA-256(serverSeed)` is compared and shown. Status stays **"Commitment scheme unconfirmed"** until you confirm the scheme in Settings | That the hash existed before the round. A hash typed in later proves nothing about timing |
| … + confirmed commitment scheme | **Commitment verified / mismatch** | Timing |
| … + independently timestamped, confirmed pre-round publication | Required for **"Verified with sufficient evidence"** | That the operator cannot manipulate seeds in other ways |

Status fields are kept separate:

* **Outcome**: Reconstructed, Match, Mismatch, Missing comparison, Invalid input, Unsupported version
* **Commitment**: Verified, Mismatch, No commitment supplied, Scheme unconfirmed
* **Timing**: Pre-round publication verified, or Publication timing unverified (the only value the lab currently produces; see the On-chain section)
* **Final assessment**: Verified with sufficient evidence · Result matches, commitment timing unproven · Reconstructed only · Mismatch (result) · Commitment mismatch · Incomplete evidence · Unsupported algorithm

Every result also carries a **Reported vs Reconstructed** table, field by field. When you open a stored record, the Lab recomputes it from the stored inputs and shows whether that reproduces the stored outcome exactly.

For independent reproduction, **Round History → Standalone script** downloads a self-contained Node.js file (`node round-<id>.mjs`). It recomputes the round without this application.

**Payouts:** authentic Solpump Keno payout tables were not independently established, so payout verification is reported as *unavailable*. Match counts are still verified. No payout multipliers are invented.

**On-chain:** Solpump's program IDs and event formats were not confirmed, so the On-Chain Evidence page is a generic, read-only Solana transaction viewer. It shows slot, block time, programs, logs and memos, and checks whether values you supply appear in the transaction. It decodes nothing Solpump-specific and never marks timing as verified on its own.

## Importing history

You can import CSV, JSON (an array, `{ "rounds": [...] }`, or a single object), JSONL, or pasted text, up to 50 MB per import. Keys can be snake_case or camelCase.

The browser uploads a file **in pieces**. Each piece is verified and committed before the next is sent, so you can watch progress, pause, resume or cancel, and a cancelled or failed import keeps only complete records. Keep the page open until the import finishes; an import that stops receiving pieces is shown as interrupted after 10 minutes. Each row is verified on its own; malformed rows are listed with their line number in the original file, without discarding the rest. A piece that is sent twice (for example after a dropped connection) is stored only once.

Rounds that are **already stored are skipped**, so re-importing a file is safe. Give large nonces and round IDs as text, not JSON numbers: a JSON number beyond 2^53 has already lost digits and is rejected.

```
round_id,game,algorithm_version,server_seed,client_seed,nonce,difficulty,selected_numbers,grid_size,mine_count,clicked_tiles,index_base,card_count,reported_outcome,commitment,timestamp,source
```

* `reported_outcome` means:
  * **crash**: the multiplier
  * **blackjack**: cards such as `KC 7H AS`
  * **keno**: the 10 drawn numbers
  * **mines**: the mine positions, or `win`/`loss`
* `index_base` is `0` (default) or `1` for Mines positions and clicked tiles.
* `algorithm_version` is `hmac_sha256_v2` (or `v2`) or `seedrandom_v1` (or `v1`/`legacy`). It is required for Keno and Mines.

## Security model

This is a single-user tool. Locally it has no login unless you set `SFL_PASSWORD`; a hosted deployment always requires one.

* **Network exposure.** It listens on `localhost` only. It answers only requests whose `Host` is localhost, 127.0.0.1 or [::1], which protects against DNS rebinding.
* **Cross-site requests.** Any request that changes data must come from the app's own origin.
* **Untrusted data.** Imported files and RPC responses are size-limited and validated.
* **Exports.** CSV exports neutralise spreadsheet formulas; HTML reports can't run scripts.
* **Exposing it deliberately.** Setting `HOST`/`SFL_ALLOWED_HOSTS` without `SFL_PASSWORD` exposes every stored seed to the network, so only do it on a trusted network. The app prints a warning.
* **Login (hosted, or local with `SFL_PASSWORD`).** One password, compared in constant time; failed attempts are slowed and throttled. The session is a signed, expiring (12 h) token in an `HttpOnly`, `SameSite=Strict`, `Secure` cookie, with nothing stored on the server. A hosted deployment without `SFL_PASSWORD` refuses every data request rather than running open.

## Deploying to Vercel

The same code runs on Vercel, with the records in a hosted [Turso](https://turso.tech) (libSQL) database instead of the local file. The static app is served by Vercel and the API runs as one serverless function (`api/index.mjs`, bundled by `npm run build:api`). Local use with `start.bat` is unchanged.

1. Create a Turso database (Vercel Marketplace → Turso, or the Turso dashboard) and copy its URL (`libsql://…`) and an auth token.
2. Import this GitHub repository as a Vercel project. The build settings come from `vercel.json`.
3. In the project's environment variables, set:

   | Variable | Value |
   |---|---|
   | `TURSO_DATABASE_URL` | the `libsql://…` URL |
   | `TURSO_AUTH_TOKEN` | the database auth token |
   | `SFL_PASSWORD` | a long, random password (the only login) |
   | `SFL_SESSION_SECRET` | optional: a random string of 32+ characters; changing it signs everyone out |
   | `SFL_ALLOWED_HOSTS` | optional: custom domains, comma-separated (the `*.vercel.app` domains are allowed automatically) |

4. Deploy. The schema is created on the first request.

What differs when hosted:
* **Data location.** Records, including revealed seeds, are stored by Turso and the API runs on Vercel. Revealed seeds are not secret, but the data leaves your machine.
* **Backups.** The "Create database backup" button is replaced by Turso's own backups and point-in-time restore. The JSON export remains a portable copy.
* **Imports.** Files are uploaded in pieces of about 400 KB, which keeps every request under Vercel's request size limit.

## Tests and quality gates

```
npm run audit:all          # everything below, with a PASS / FAIL / SKIP summary
npm run typecheck          # strict TypeScript, backend + frontend
npm run lint               # ESLint (no `any`, no Math.random)
npm test                   # 92 unit + reference-parity tests (incl. 11 mutation tests)
npm run test:parity        # 2,055-case three-way parity run (prod / JS reference / Python)
npm run test:integration   # 48 API, security, migration, import-job, script and export tests
npm run test:e2e           # 18 Playwright browser tests on a throw-away database
npm run build              # production frontend build
npm run bench -w backend   # performance benchmark (1k / 10k / 100k rounds)
```

The Python parity step needs Python 3 on `PATH`. If Python is missing, `audit:all` reports it as SKIPPED; it never counts as passed.

The supplied vectors and the sample CSV are **synthetic**. They show the code matches the published reference algorithms. They are **not** evidence of compatibility with live Solpump rounds. That needs genuine historical rounds.
